## 1. Objectif et critères d'acceptation observables

1. Chaque **déploiement de production** a une identité unique et vérifiable — son identifiant de déploiement Vercel (`dpl_…`) avec le commit — et un **libellé lisible** fixé automatiquement à la compilation (date et heure UTC de compilation), sans intervention manuelle, sans compteur ni registre. Le libellé seul n'est pas garanti unique (deux compilations dans la même seconde) ni ordonné selon les mises en production : il est toujours affiché avec `sha7`, et aucune comparaison de version ne repose sur son ordre (révision R12).
2. Un retour arrière (promotion d'un ancien déploiement Vercel) affiche le numéro de ce déploiement-là (celui réellement servi) — par construction.
3. Un déploiement d'aperçu n'obtient **jamais** de numéro de production ; il s'affiche « Aperçu · <sha7> ».
4. Page « Informations sur l'application » accessible à tout utilisateur connecté depuis le menu du profil, affichant des valeurs réelles ou « Non disponible », et distinguant : version Web **disponible** (serveur), **téléchargée/prête**, **exécutée** (page en cours).
5. La mise à jour Web n'interrompt jamais un travail : jamais de rechargement automatique sur une fiche projet, ni avec un champ actif, ni avec des opérations en attente (saisies OU photos), ni hors ligne, ni pendant une synchro. Indication discrète « Mise à jour prête — appliquer maintenant ».
6. La page admin « Appareils » montre par appareil : collaborateur, type, système, version native + build (si connus), version Web exécutée (numéro), dernière disponible, dernier contact, dernière vérification, statut de mise à jour, état de synchro ; « Dernier état connu (date) » au-delà d'un délai sans contact ; signalement d'une app native sous le minimum requis.
7. Aucune régression : suites unitaires et e2e existantes vertes ; hors-ligne, coffre, service worker inchangés dans leur comportement.

## 2. Approche

### 2.1 Identité d'une version Web — fixée à la compilation (révision des tours 1–2)
Un compteur séquentiel fiable exigerait un stockage durable **transactionnel** (écriture conditionnelle, protection contre un détenteur de verrou expiré) : la liste KV Notion n'en offre pas (R7 : lecture-modification-écriture multi-étapes ; R8 : contenu illisible relu comme liste vide), Redis seul n'est pas la source durable du projet, et Git est inutilisable à la compilation (clone partiel de profondeur 10). Conformément à la consigne de l'utilisateur (« si une numérotation séquentielle n'est pas suffisamment fiable, propose une solution plus robuste »), **le numéro lisible est déterminé à la compilation, sans registre** :
- **Identité** = `deploiement` (`dpl_…`, unique par déploiement Vercel) ; à défaut (local) `sha`. Toutes les comparaisons (exécutée vs disponible, statut appareil) se font **par égalité** de cette identité, jamais par ordre de libellé (révision R12).
- **Libellé lisible** = horodatage UTC de la compilation : `AAAA.MM.JJ-HHMMSS` (ex. `2026.10.19-174552`), affiché « Version Web 2026.10.19-1745 · a1b2c3d » (avec `sha7`). Il dit *quand* le code a été compilé, identique sur tous les appareils, connu **dans la page elle-même** (donc aussi hors ligne). Il n'est pas présenté comme unique ni comme ordre de publication : un retour arrière affiche volontairement un libellé plus ancien, qui est celui réellement servi.
- Identifiants techniques affichés avec : `sha7` (commit) et `deploiement` (`dpl_…` Vercel).
- `env` : `production` → « Version Web … » ; `preview` → « Aperçu · sha7 » (jamais confondu avec une production) ; local → « Développement ».
- Retour arrière (promotion d'un ancien déploiement Vercel) : le déploiement restauré sert **sa** page, compilée avec **son** horodatage → la version affichée est celle réellement servie, sans aucun état à corriger.
- Redéploiement du même commit (nouveau `dpl`) : nouvelle compilation → nouveau numéro (c'est bien un nouveau déploiement).
- Mise en œuvre : `src/lib/version-compilation.ts` (déjà en place, relevé à la compilation via `next.config.ts` → `process.env.TM_VERSION_COMPILATION`) ajoute `numero` (dérivé de `compile`). `layout.tsx` publie `<meta name="tm-version" content={JSON compact: numero, sha, deploiement, env, compile, dateCommit}>` ; le diagnostic `tm-version-diag` est retiré ; `tm-build` (sha) reste pour compatibilité des pages ouvertes.
- **Aucun registre, aucun compteur, aucune écriture Redis/Notion** pour le versionnement : les constats R2, R3, R4, R7, R8, R11 n'ont plus d'objet. Historique Git/Vercel retrouvé : rapporté à l'utilisateur, non transformé en numéros.

### 2.2 `/api/build` (étendu, compatible)
- Réponse : `{ build (sha, inchangé), version: {numero, sha, deploiement, env, compile, dateCommit}, coqueAppleMinimum }`, `Cache-Control: no-store`, aucune lecture Notion/Redis : la route renvoie la version **compilée dans le déploiement qui répond**, c'est-à-dire la version disponible en production.
- Reste derrière l'authentification actuelle (middleware).

### 2.3 Version exécutée vs disponible vs téléchargée
- **Exécutée** = balise `tm-version` du document courant (en mémoire, par document — R6).
- **Disponible** = `version` renvoyée par `/api/build` (observation serveur datée, partageable entre onglets via `localStorage` `tm-maj-observation`).
- **Téléchargée / prête** = la nouvelle coquille a été récupérée du réseau, vérifiée (sa balise `tm-version` = la version disponible) et **mise en cache par le SW** (voir 2.4) ; elle n'est « exécutée » qu'après rechargement.
- Pages anciennes (avant ce changement) : pas de `tm-version` → « Version Web : non disponible (ancienne page) » + sha depuis `tm-build` ; elles se mettent à jour par le mécanisme actuel.

### 2.4 Détection et application des mises à jour (`maj-auto.tsx` refondu + `src/lib/etat-mise-a-jour.ts`)
- États : `a-jour`, `disponible`, `preparation`, `prete`, `hors-ligne` (vérification impossible), `natif-obsolete`, `en-attente-synchro` (prête mais retenue par des opérations).
- Vérification : toutes les 90 s, au retour visible/focus, au retour du réseau. Compare **par égalité** `version.deploiement` serveur à celui de la balise `tm-version` du document (repli : `sha` via `tm-build`).
- **État par document** (révision R6) : la version exécutée et l'état de mise à jour vivent **en mémoire de la page** (module + évènement `tm-maj-etat`), dérivés des balises de CE document. `localStorage` ne garde que des **observations serveur datées** (`tm-maj-observation` : version disponible, numéro, date de vérification), partagées sans risque entre onglets. Le battement de chaque onglet envoie la version que CET onglet exécute ; le serveur garde le dernier battement reçu (politique explicite : « dernier onglet actif de l'appareil »).
- **Préparation (« téléchargée »), tout-ou-rien** (révision R13) : quand une nouvelle version est disponible, la page demande au SW `PREPARER_VERSION {deploiement}`. Le SW travaille dans un **cache temporaire** `tm-prep-<deploiement>` : (1) récupère `/` par le réseau et vérifie que sa balise `tm-version` porte le `deploiement` visé ; (2) calcule la **fermeture** de cette coquille (fragments cités par le HTML puis, de proche en proche, par le JS, et ressources citées par `url(...)` dans les feuilles de style, résolues depuis leur adresse — polices — révision V22) avec une comptabilité stricte : toute réponse non OK, erreur réseau, erreur d'écriture, ou dépassement de la limite (1 500 fichiers) = **échec** ; (3) seulement si tout est complet : publie dans `CACHE_NAME` d'abord les fragments (AJOUTS seulement : adresses à empreinte, aucune entrée existante remplacée ni retirée), puis les métadonnées de rétention, puis **en dernier, en une seule écriture**, le HTML `/` ; supprime le cache temporaire. En cas d'échec (révision V23 — invariant précisé) : cache temporaire supprimé, **aucune entrée existante de `CACHE_NAME` modifiée ou retirée**, ancienne coquille intacte ; des fragments à empreinte déjà ajoutés peuvent subsister, inertes et nettoyables ; aucun échec n'est possible après l'écriture de `/`, réponse `VERSION_NON_PREPAREE` ; nouvel essai au prochain contrôle. Succès : `VERSION_PRETE` (état « prête » = « la nouvelle coquille et toute sa fermeture ont été téléchargées et vérifiées »). Une seule préparation à la fois (verrou en mémoire du SW). La fonction de crawl existante (`completerLesFragments`, tolérante aux erreurs) reste utilisée pour le pré-cache opportuniste, pas pour la préparation.
- **Portée de la garantie (révisions R15, R17 — garantie resserrée plutôt que protocole étendu)** : la sûreté de l'application **ne repose pas** sur un rechargement hors ligne. L'application (automatique ou manuelle) n'a lieu **qu'en ligne** ; le rechargement charge alors la nouvelle version par le réseau. Si le réseau tombe pendant le rechargement, le navigateur sert ce que le cache contient — et comme **aucun cache n'est vidé**, c'est une coquille déjà présente avant (l'ancienne, intacte avec ses fragments, ou la nouvelle si sa préparation a réussi) : exactement le comportement d'une ouverture hors ligne aujourd'hui, jamais pire. L'état « prête » est une information (« téléchargée »), pas une promesse d'exécution hors ligne de toutes les pages. Les écritures opportunistes existantes (navigation réseau, `PRECACHE_URLS`, installation) restent **inchangées** : leur comportement hors ligne pour les pages autres que `/` n'est ni modifié ni revendiqué par ce plan (limite existante, signalée dans le rapport, hors périmètre).
- **Application automatique** seulement si TOUTES les conditions : page visible, en ligne, chemin ≠ `/projet/…`, aucun élément éditable focalisé, aucune interaction depuis 60 s (pointeur/clavier/tactile), file de saisies vide, **file de photos IndexedDB vide** (statut pending), aucune synchro en cours (`processQueue`/`processPendingUploads` actifs), aucune finalisation en attente d'envoi, aucune fenêtre ouverte — boîtes déclarées (`role=dialog/alertdialog`, `aria-modal`, `<dialog open>`) **et** calques plein écran sans rôle (élément fixe, visible, qui capte le toucher et couvre ≥ 90 % de l'écran), comme les éditeurs « Nouveau projet » ou « Préférences e-mails » (révision V19). Les files sont lues **strictement** : une file illisible compte comme non vide (révision V20). Les éditeurs à brouillon non enregistré sans champ actif (ex. droits d'accès) se déclarent (`marquerTravailNonEnregistre`) et retiennent l'application, même manuelle. L'inactivité se compte à partir du chargement et du retour au premier plan, jamais « infinie » au démarrage. Après trois préparations ratées pour une même version, la pastille propose l'application manuelle (réseau requis) plutôt que de laisser l'appareil sur l'ancien code sans le dire. État « prête » requis pour l'application automatique. Une seule tentative par version (sessionStorage), comme aujourd'hui. Sinon : pastille discrète non bloquante « Mise à jour prête — appliquer maintenant ».
- **Application manuelle** (bouton) : autorisée hors fiche projet et sans champ focalisé, même avec des opérations en attente (elles sont persistées et reprennent — prouvé par e2e/60–62) ; message clair du nombre d'opérations reprises. Sur une fiche projet : bouton présent mais demande de confirmation explicite. **Interdite hors ligne** (révision R5).
- **Appliquer = recharger, sans purge** (révisions R9, R10) : on ne supprime **aucun** cache. Juste avant le rechargement : recontrôle de toutes les conditions (dont « en ligne » et un aller-retour réussi à `/api/build` < 5 s qui confirme encore la version visée) ; sinon pas de rechargement. L'ancien message `PURGE_APP_SHELL` reste accepté par le SW pour les pages anciennes : il reçoit sa réponse `APP_SHELL_PURGED` mais **n'efface plus rien** (relecture indépendante, point 5) ; il n'est plus envoyé par le nouveau code.
- **Les autres onglets** restés sur l'ancienne version gardent leurs fichiers : rien n'est effacé à l'application. À l'activation du SW : sont supprimés seulement les caches `tm-rapport-*`/`tm-static-*`/`tm-api-*` d'une **ancienne valeur de `VERSION`** (ce changement ne modifie pas `VERSION`) et les caches temporaires `tm-prep-*` abandonnés ; jamais `tm-versions-meta`. **Pré-caches (révision R18)** : avant de supprimer un `tm-precache-*` dont le nom diffère du courant, le SW **recopie** chacune de ses entrées absente de `CACHE_NAME` dans `CACHE_NAME` (puis supprime l'ancien) : une page qui dépendait d'un fichier de l'ancien pré-cache le retrouve (le gestionnaire statique et la recherche approximative consultent `CACHE_NAME`). Si une recopie échoue, l'ancien pré-cache est **conservé** (nouvel essai à l'activation suivante). Au plus un pré-cache supplémentaire subsiste donc. (Mesure : en production `PRECACHE_VERSION` servi = constante du dépôt, le cas ne survient qu'à un changement commité de `sw.js` ; il est testé en simulant un changement réel de nom.)
- **Rétention par versions utilisées** (révision R14, remplace tout critère d'âge HTTP) : métadonnées locales `tm-versions-meta` (une entrée JSON par `deploiement` : `racines` = scripts/feuilles chargés par la page, `vuLe`). Chaque page signale `VERSION_EN_USAGE {deploiement, racines}` au chargement, au retour au premier plan et toutes les 5 min. **Ensemble conservé** = fermeture, calculée **depuis les caches seulement** (aucun réseau), de : toutes les entrées HTML en cache ∪ racines des versions signalées depuis moins de 7 jours. Le nettoyage (au plus une fois par jour, en ligne, déclenché après chaque signal d'usage enregistré et après une préparation réussie — révision V24 — et exécuté en série avec les préparations, jamais pendant) supprime des caches `tm-rapport`/`tm-static` uniquement les entrées `/_next/static/…` **hors de l'ensemble conservé**. Toute erreur de lecture pendant le calcul **annule** le nettoyage (rien supprimé). Métadonnées **absentes** ≠ **illisibles** (révision V21) : illisibles → aucun nettoyage ; pour ne pas rester bloqué, la liste est reconstruite à neuf **et la reconstruction est notée** : le nettoyage s'abstient alors pendant toute la durée de rétention (7 jours), le temps que chaque onglet ouvert ait redit ce qu'il utilise. Le nettoyage relève la liste des entrées supprimables AVANT de calculer l'ensemble conservé et abandonne si une écriture de cache survient pendant le calcul (compteur d'écritures). Les caches `tm-prep-*` abandonnés sont jetés au début de chaque préparation. La fermeture suit aussi les `url(...)` des feuilles de style. Une page restée ouverte signale sa version, donc ses fragments — y compris ceux qu'elle chargera à la demande, cités par son code — sont conservés, quelle que soit la date HTTP des fichiers. Risque résiduel documenté : un onglet suspendu plus de 7 jours sans signal, rouvert hors ligne, peut manquer un fragment ; en ligne il se met à jour.
- **Service worker (révision R1)** : l'activation ne **renavigue plus** les fenêtres (`fenetre.navigate` supprimé). `skipWaiting`/`clients.claim` conservés ; message `SW_ACTIVE` aux pages.
- Natif obsolète : réutiliser `controlerCompatibilite()` (coque < `COQUE_APPLE_MINIMUM`) ; état exposé.

## 4. Risques et parades
- Mise à jour bloquée indéfiniment par une file jamais vide : état visible « Synchronisation en attente » + application manuelle.
- Versionnement : aucun état serveur → pas de course, pas de perte, pas de doublon possible entre compilations distinctes ; même seconde → distinguées par `deploiement`/`sha` affichés. Horloge du serveur de compilation Vercel supposée juste (UTC).
- Page ancienne sans `tm-version` : « non disponible (ancienne page) » + sha.
- Croissance des caches SW (plus de purge à l'application) : rétention par versions réellement utilisées (7 jours sans signal) ; taille mesurée en e2e. Risque résiduel documenté : un onglet suspendu plus de 7 jours puis rouvert **hors ligne** sur une version libérée peut manquer un fragment jamais chargé ; en ligne il est simplement mis à jour.
- Battement plus lourd : quelques champs courts ; fréquence inchangée.
- SW : modifications limitées à : suppression de la renavigation forcée à l'activation (R1), préparation tout-ou-rien en cache temporaire, recopie des anciens pré-caches avant suppression (R18), signal `VERSION_EN_USAGE` et nettoyage par ensemble conservé (R14) ; les stratégies de lecture (réseau d'abord, cache des API, exclusions PDF) sont inchangées ; `/api/build` déjà exclu du cache SW. Ancienne page restée ouverte : continue sur ses fichiers en cache ; vérifiée en e2e (deux fenêtres, dont une fiche projet avec saisie, au moment d'une mise à jour du SW : aucune ne recharge).
- Régression `MajAuto` : tests e2e avec ancienne/nouvelle version simulées.
